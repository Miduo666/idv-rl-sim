## ‼️ 最高优先级 · 读内存只走两条隐蔽通道，严禁 /proc/pid/mem 跨进程读（2026-10-15 踩雷）

**这个游戏有网易反作弊，会检测外部进程读它的 `/proc/self/{mem,maps,pagemap,fd}`（+ TracerPid）。**
2026-10-15 实测：用 PC 侧 `/proc/16160/mem`+dd 的跨进程工具抓大厅/准备/局内，**游戏弹出"检测到修改客户端"警告**。

**那句话只针对缺页、没考虑反作弊监控 /proc，是错的**（已在那边一并纠正）。
它们只适合**没有反作弊**的目标（物种起源/荒野日记那类），不适合第五人格。

## ★ 国际服(com.netease.idv.googleplay)适配 —— 2026-10-23 局内实测通

国际服和国服(com.netease.dwrg)最大不同：**引擎 so 不是独立 libclient.so，而是打包在
`split_config.arm64_v8a.apk` 里直接 mmap**（无 castor 热更路径）。实测 r-xp 段 154MB、apk 内文件偏移 `0x2618000`、
段起点即 ELF 头（首个 LOAD 仍是 R E vaddr0，同国服）。引擎 bss = 其后的 `[anon:.bss]` 匿名段(实测 30MB)。
三处修复（都在国际服分支，国服路径不受影响，已上机：产物 `rgpyokcq.sh`）：
1. **libbase**(`draw_Gui.cpp` read_thread)：`is_official`(=含 com.netease.idv) 分支改成
   `strstr(line,"com.netease.idv") && (t-a)>0x5000000` 取引擎 r-xp 段起点；原 `strstr(line,".")` 会取到第一个系统 so，错。
2. **bss**(`get_module_bssgjf`)：`is=true` 触发条件从国服 size `==114982912` 改成
   `strstr(line,"com.netease.idv") && r-xp && (taddr-addr)>0x5000000`，随后取 `[anon:.bss]`(匿名 rw-p、strlen<86、>3000页)。
3. **PyRoot::read_elf**：`fopen(so路径)` 后**按 maps 行的文件偏移 seek**(apk 内偏移，国服独立 so 时为 0)再读 ELF 头/段表/strtab；
   否则 apk 偏移 0 是 ZIP 的 PK 头、`memcmp("\x7fELF")` 失败 → read_elf 返回 false → 退回国服写死槽 → 国际服 Python 层全灭。
实测日志：`[基址] libbase=0x7A7A852000 BSS=0x7A84F71000-0x7A85DE9000`、`[Py根] ...split_config.arm64_v8a.apk .PyRuntime 命中`、
dict/int/float/True/False 全解出、`[实体]` 读出带中文名坐标。**场景签名(矩阵/数组)自愈扫描在国际服 bss 里一样命中**。
⚠ 分支按 `com.netease.idv` + 巨型段匹配，webview(157MB,路径 com.google.android.webview)被排除；国际服大版本若改 split 结构需重看 maps。

## 这是什么

用户在长期维护一个第五人格(com.netease.dwrg)的 ESP 叠加层工具（内核驱动读内存 + ImGui 绘制坐标/阵营/道具），
以及一个独立的"骨骼与进度"Python注入子系统（ptrace 注入 + hook 游戏内嵌的 CPython 解释器）。
游戏每次热更新都可能让写死的内存偏移失效，需要重新定位。

这个 skill 的作用：新开对话时快速恢复上下文，并且**直接给出已经验证过的排查路径**，
不要再从"要不要开 IDA"这种问题开始。

### 内存里其实有两层，先分清楚在找哪一层

| | 场景对象层 | Python 层 |
|---|---|---|
| 是什么 | bss 签名扫出来的那个 290 项指针数组，元素是**渲染节点**（类名是 `.gim` 路径） | 游戏内嵌 CPython 堆上的 `XxxUnit` 实例 |
| 有什么 | 坐标、朝向、是否本局存在、类型 | **全部玩法状态**：破译进度、开门进度、椅子状态、本机玩家身份 |
| 怎么读 | 写死/自愈的结构体偏移 | 走对象图（dict 按名字查） |

**关键结论：场景对象身上一点玩法状态都没有。** 想要"进度/状态/归属"这类东西，
直接去 Python 层，别再在场景对象里扫 —— 那条路已经彻底走死过一次（见 `python-layer.md` 第一节）。

> **★ 方法论铁律（2026-10-15，逆 007 期间学到）：找任何游戏数据前，先问"它是不是 Python 层的命名字段"，再决定要不要上差分 / 字节扫描。**
> Python 层的东西都带名字（`ui_dict` / `genius_id_lv_lst` / `cured_process_client`…），按名字找是**最高信号**的路；
> 原生场景对象层只有裸偏移，盲差分信噪比极低。正确顺序：
> 1. **先在 Python 层按名字找** —— 跨进程 `py_scene.py` / `py_named.py` / `py_chain.py`（靠 `pyw`+`devread`，不需注入，只要前台），或注入后进程内直接 `getattr`；
> 2. 名字找不到、或只有场景对象层（坐标 / 渲染）才有的，才回到原生偏移 + 差分。
>
> 实例：区分"大厅 / 准备 / 局内"一开始拿相机链做字节差分，扫了半天三态只有动态计数在变、没有稳定判据；

## ！！先排除这个：内存压力造成的"偏移失效"假象 ！！

**2026-09-20 花了一整轮才定位。用户报"突然几乎不绘制了"时，这是第一个要排除的，
不是最后一个。** 它看起来跟偏移失效一模一样，但跟代码、跟热更新完全无关。

> **★ 2026-10-15：用户换了新手机，16GB 内存（旧机 `MemAvailable` 只有 7.03GB 总量，见下面现场数据）。**
> 这类"内存压力 → 前台游戏工作集被压进 zram → 驱动读换出页返回 0 → 类名链/Python 冷页读不出"的假性失效，
> 在 16GB 机上**预期大幅减少甚至基本不出现**（尤其天赋这种开局后不再访问的冷页）。
> 下面整节仍然保留：① 判据方法（`VmSwap` 对 `VmRSS`）通用；② 万一在新机上仍撞到（极端多开/后台压力），照样按这里排查。
> `PyGenius.h` 的锁存 / 增量累积 / "读失败沿用缓存"那些加固仍留着，只是以后更少触发。

> **2026-09-23 第二次出现，这次几分钟就结案了**：用户报某个求生者对象不显示、过一会又自己好。
> 判据链：**自愈 → 只可能是内存**（偏移/逻辑错误不会自愈）；**绘制调试里也没有类名 → 类名链读不出**；
> 当时 `VmSwap 1040MB > VmRSS 717MB`。事后 PC 侧复查该对象一切正常（类名链完整、`+0x240=2`、坐标正常、
> 所有过滤都通过），正是"已经恢复"的样子。
> ⚠️ 一并排除过的干扰项：那轮刚把 `Count` 兜底值从 3000 改成 1000，看着可疑但**不可能**——

### ⚠️ 备查：驱动“读内存超写”导致进程被静默杀死（2026-09-25，朋友机器上撞到，用户本机未复现）

**现象**：叠加层进程跑着跑着没了（像掉后台），没有崩溃提示。
**确诊信号**：日志里出现 `读内存超写：请求 N 字节，多写了约 M 字节` → 根因已确认是**内核驱动的问题**：
一次 `OP_CMD_READ` 实际写回用户缓冲的字节数 > 请求的 `size`。

**为什么会被杀**（推断，机制上成立）：`kerneldriver-qxqd.hpp` 的 `T read(addr)` 把 `T result{}` 放在**栈上**、
直接当 ioctl 目标缓冲。驱动多写 M 字节就踩坏相邻栈（返回地址 / stack canary / 别的局部变量）
→ SIGSEGV 或 `__stack_chk_fail` abort，进程直接消失；`read(addr, buf, size)` 传进来的堆/全局缓冲同理会踩坏邻居。

**修法：在驱动对接层（`kerneldriver-qxqd.hpp` 的 `read(uintptr_t, void*, size_t)`，约 92 行）加中转缓冲**，
上层调用一律不用改：

```cpp
bool read(uintptr_t addr, void *buffer, size_t size) {
    if (!ready() || pid <= 0 || buffer == nullptr || size == 0) return false;
    constexpr size_t kSlack = 4096;                  // 给驱动超写留的余量
    thread_local std::vector<uint8_t> bounce;        // 读线程/渲染线程都在读 → 必须每线程一份
    if (bounce.size() < size + kSlack) bounce.resize(size + kSlack);
    COPY_MEMORY command{};
    command.pid = pid; command.addr = addr;
    command.buffer = bounce.data(); command.size = size;   // 请求的仍是 size
    if (ioctl(fd, OP_CMD_READ, &command) != 0) return false;
    memcpy(buffer, bounce.data(), size);             // 只拷回请求的部分，多写的留在中转区
    return true;
}
```

- 想确认/记录超写量：ioctl 前把 `bounce[size .. size+kSlack)` 填成哨兵字节（如 `0xCD`），之后从尾往前找第一个
  非哨兵字节，得到 M；超过 `kSlack` 说明余量不够，要加大。
- 大块读（`native-bones.md` 里一次读全部骨骼矩阵那种）也走这里，余量按页给（4KB）一般够；
  如果超写量跟 `size` 成比例，改成 `size * 2` 之类。
- `write` 方向没报过问题，不用动。
- 代价：多一次 `memcpy`，相比 3~4µs 的 ioctl 可忽略。

**用户本机没遇到，暂不改代码**；朋友那边（或换了驱动/内核后）再出现“进程静默消失”，先搜日志里有没有“超写”，有就按上面加。

### 其他已落地的细节

- **道具绘制过滤掉自己的**：必须**只算水平距离**，不能用三维距离。
  道具挂在角色骨骼上（手/胸口），挂点比角色原点（脚底）高一截：实测
  `h55_pendant_glim`（手电筒）高度差固定 `+0.73 米`、水平只差 `0.36 米`。
  三维距离因此恒有 0.7+ 米的底噪，**亚米阈值永远不成立**，跟站位无关，是结构性偏移。
  当前代码：`道具水平距离 = sqrt((D.X-Z.X)²+(D.Y-Z.Y)²)/距离比例`，阈值 **`>= 1.5f`**。
  （先上的 1.0 米实战仍有漏网，说明火箭/橄榄球这类挂件的挂点比手电筒更靠外，已调到 1.5。）
  **另一个坑**：全局的 `距离` 是 `int`（文件头 `int 距离;`），不到 1 米会被截断成 0，
  所以亚米级阈值必须用浮点重算一次，直接写 `距离 < 0.5` 是永远不成立的。
  （第 907 行的 `孽蜥距离` 算的正好就是这个水平距离，但它是全局、别处会改，别直接复用。）

### Python 层关键偏移（2026-09-21 建立，跨对局验证过）

完整说明看 [`python-layer.md`](python-layer.md)，这里只放最常用的：

```
libbase + 0xA7029E8   -> sys.modules
  "game_kernel"       -> module -> +0x10 = md_dict
    "unit_mgr"        -> UnitManager 实例
      实例 - 0x18     -> managed dict          (所有 Python 实例都这样取 dict)
        "units_by_type" -> dict(int -> list)
          键 3 = 密码机  键 6 = 大门  键 4 = 椅子  键 2 = 求生者  键 1 = 监管
            list+0x10=元素数  +0x18=元素数组
              GeneratorUnit: "fix_process"(0~100) / "model"->+0x20=场景对象 / "position"->+0x10
              大门:          "hack_process"

类型对象: PyFloat +0xA0336F0  PyLong +0xA026498  PyDict +0xA023BF0  str +0xA038140
dict: +0x20=ma_keys; keys+0x09=log2_index_bytes +0x0A=kind +0x18=nentries
      entries = keys + 32 + (1<<log2_index_bytes)，步长 16(全unicode) / 24(带hash)
```

**三条铁律**（每条都是踩过才知道的，详见 `python-layer.md` 第四节）：

1. **entries 起始必须逐实例算** —— 同一个类不同实例的 dict 形状可以不一样，套用会读到无关属性
2. **值在 int / float 之间来回变**，两种都要认；"认不出"当读取失败，**绝不能当成 0**
3. **属性每帧重新赋值、旧对象进 freelist 被复用** —— 读指针→解引用→**再读一次指针确认没变**，
   再校验 refcount>0 / 类型对 / 数值在 0~100。驱动读微秒级一次就过，adb 读则几乎必然读到垃圾

**配对场景对象用 `model`+0x20 的指针身份，不要用坐标** —— 实测一局 7 台里 4 台 `position` 读不出来。

改名 `cls` 后修好。本体集合那半边不受影响（`add_unique` 在出错那行之前）。
注意这条路径**只管局内**：准备阶段 Python 侧没有 `[1]` 单位，预知仍走类名逻辑，那边的干扰物问题仍未解决。

**为什么要按类缓存**（开销分析，16 ms 下尤其重要）：驱动每次读取就是一次 `ioctl`。原先
`another_model` 只有一个共用序号缓存，而 `ButcherUnit`(~1000 条)/`CivilianUnit`(~1300 条)/
`MyCivilianUnit` 的序号各不相同，遍历每换一个类缓存就失效、从头按名字扫（每条 2 次读取），
一轮 2~4 次、约 2,500~5,000 次读取，九成是重扫。按类缓存后每轮只剩约 250~330 次固定读取。
（单次 ioctl 耗时和序号位置是估算，没实测。）实测：**所有玩家类都有 `another_model`**
（没第二形态时是 None），所以不存在"查不到就每人扫全表"的情况。

曾考虑过"记住这局没有键 236 就不再扫"，**没采纳**：`units_by_type` 的键会在局中新增
（信徒/分身都是局中召出来的），缓存"没有"会漏读。收益也只有每轮 ~80 次读取。
若要做，必须以 `ubt.ma_keys` 指针 + `dk_nentries` 任一变化为失效条件（3.11 新增键必然改变其一）。

### `PyCore.h`：三个模块共用的 CPython 工具（2026-09-23）

`is_obj` / `str_equals` / `Dict`+`read_dict` / `key_slot`/`value_slot` / `find_key` / `resolve_index` /
`get_attr` / `get_inst_dict` / `read_int` / `read_number(lo,hi)` / `read_bool` / `read_list` /
`get_type_list` / `game_kernel_dict` / `get_scene_obj`。类型对象和 True/False 一律取自 `PyRoot::`。

**合并时踩到/避开的三个坑，改这个文件前必看**：

1. **`g_entry_block`(48KB) 和驻留键指针表必须是 `thread_local`。** 三个模块各跑一个线程
   （16/100/500ms），合并前分属三个命名空间天然隔离；照搬成普通 `static` 就是实打实的数据竞争。
2. **`read_list` 的语义一个字都不能改**：`n>256` 算读到垃圾（放宽会让 16ms 那个线程按垃圾 n 空转几千次读）；
   **空列表是成功**（n=0, items=0）不是失败（"读不到"和"真的是空"必须分开，天赋那边踩过）；非空时 items 必须合法。
   我第一版写成 4096 + 空当失败，靠对 `git diff` 才发现。
3. **值域闸留在各模块**：进度 0~100、冷却 0~600，统一成一个范围就会互相破坏。
4. 共享函数全部 `inline`（C++17 跨 TU 只有一份实例），所以以后别的 `.cpp` 再包含这些头也不会
   悄悄多出一套独立状态 —— 这正是原来"头文件里放 static 状态"那个隐患的解法。

### 类名缓存：一轮 12ms → 9ms，但它是**下次出怪问题时第一个要怀疑的**

类名要走五跳指针 + 长度 + 内容共 7 次读，一轮 300 个对象就是 2000 多次，占了整轮的一半。
现在按 `对象地址 -> {第一跳指针, 类名}` 缓存，每轮仍读一次 `obj+0xf8` 校验，**7 次降到 1 次**。

⚠️ **地址会被复用**，校验只看第一跳指针，所以理论上存在"新对象的第一跳恰好相同 → 用了旧类名"。
后果是某个对象错一轮标签。**如果以后出现"某个角色换形态/换模型后名字卡住不变"，先怀疑这里**

### Py 侧字典查找：整块读 + 驻留键指针

`find_key`/`resolve_index` 原来每比一个键要 3 次读。现在 entries 一次 `vm_readv` 读完（1300 条 × 24 字节 = 31KB，

⚠️ 原建议说"只要整块读就能降到 1 次"是**错的** —— 整块读只拿到键指针，比名字仍要逐个读字符串，

指针比不上退字符串比较），最坏只是回到原速度，不会读错。

## ！！跨进程脚本读不了"每帧重新赋值"的字段 ！！

**这是一条硬边界，不是调参问题。** 2026-09-22 在大门 `hack_process` 上量化了：

| | `hack_process`（大门） | `fix_process`（密码机，已破译完） |
|---|---|---|
| 清缓存后连取两次值指针 | **40/40 都变了** | 3 轮 30 秒纹丝不动 |
| 通过防竞态校验 | 0 次 | 21/21 第一次就过 |

`hack_process` 每帧被赋成一个**新的 float 对象**，而 `devread` 一次 fetch 是
push+shell+pull 三次 adb 往返（~0.4 秒），指针早就失效了。
驱动侧"取指针→解引用→重读指针"是微秒级，对 16ms 的重赋值有三四个数量级余量。

**诊断法**（可复用）：清缓存后连续取两次值指针，**持续不相等就只能走驱动**，
脚本侧加再多重试都没用。

**三个连带教训**：

1. **`devread.fetch` 会跳过已缓存页**（`pages = {...} - set(self.cache)`）。
   所以不清缓存的"重读指针确认没变"是**空操作**，时序实验每轮必须 `m.cache.clear()`。
   这个坑今天踩了两次（`hack_process` 一次、切视角采样一次，后者导致 25 轮采样
   全在同一秒完成、结果"相同"是构造出来的而不是观测到的）。
2. **值域校验不能省**。垃圾值里出现过 `0.16` 这种"看着完全合理"的，
   只靠指针稳定挡不住；`PyProgress.h` 的 `读数值()` 那道 `0~100` 闸才是真正挡住它的。
   注意冷却是 0~600 秒级（闪现 `csv_cd_time` 就 150），**不能套进度那条 0~100 的闸**。
3. **`py_chain.py` 把 `d0` 算出的 `VOFF` 套到所有实例上**，违反
   `python-layer.md` 铁律 #1。实例间 dict 形状可以不同，要逐实例 `dget` 按名字取。

### 调试绘制是独立分支，别忘了它

`Debugging`（UI 上的"绘制调试"开关）在 `if (W>0)` 里**单独一条分支**，

## 2026-09-17 那次热更的完整案例（照着复盘最快）

现象：用户报"基址没用了，偏移不确定还在不在"。面板显示 `数组偏移=b40a638`
但 `矩阵地址/数组地址/矩阵偏移` 全是 0。

诊断链条：

1. **`数组地址=0` 是假象**。扫描循环退出条件是 `MatrixOffset!=0 && ArrayaddrOffset!=0`，
   矩阵没命中就出不了循环，`Arrayaddr = getPtr64(...)` 那行压根没执行到。
   **看到多个值同时为0时，先确认它们之间有没有这种依赖关系，别当成多处失效。**
2. dump bss → 矩阵签名**还在**，而且 8 字节对齐，扫描逻辑没问题
3. 真正失效的只有 `签名+0x430`（该处恒为0）→ 附近发现 `+0x330/+0x3B8/+0x440`
   三个间隔 `0x88` 的同族指针 → 三个都走得通 → 整体位移了 `0x10`
4. 对象结构体：局内实测 `+0x1a0==450` 正好 5 个，类名读出 `dm65_butcher_sxwd`(小丑)、
   `h55_survivor_w_xiangshuishi`(调香师) 等 → **结构体完全没变**
5. 相机 `Matrix-0x290` 恒为 `(0,0,0)` → 用 VP 矩阵反解相机坐标当校验器，
   在窗口里找到真正的字段在 `-0x1e0`

**结论：一次热更只改了两个数（一个 +0x10 位移，一个相机字段搬家），结构体零改动。**

## 热更新的先验：核心数据不变，只动一点点偏移

（朋友给的经验，2026-09 记录）第五人格的热更新绝大多数只是给角色加几个新动作、
上新角色，**核心数据结构不会改**，变的只是少量偏移或基址，而且新值**就在旧值附近，
不会跑远**。

所以热更后的默认假设应该是「**位移了一小段**」，而不是「引擎大改、要从头找」。
排查顺序照这个先验来：

1. 先在旧值附近开窗口扫（这正是下一节 `draw_Gui.cpp` 里矩阵根 `+0x300~+0x500`、
   相机坐标 `-0x400~-0x40` 两处自愈扫描的依据）
2. 窗口里扫不到再考虑签名/结构体本身变了
3. 最后才是"引擎大改"——实际极少发生

上一节 2026-09-17 那次热更是这条先验的正面样本：**结构体一个字节都没动**，
只有两个数变了 —— 矩阵根整体位移 `0x10`（`+0x430` → `+0x440`），
相机坐标字段从 `-0x290` 搬到 `-0x1e0`。两个都在几百字节的窗口内，窗口扫描直接命中。

**适用范围要分清**（这条是本地补充，不是朋友原话）：

- ✅ **结构体字段偏移、bss 里的签名/数组槽位** —— 先验成立，附近窗口扫得回来。
  本 skill 里所有"已确认偏移全表"的条目都属于这一类。
- ⚠️ **`.so` 代码段里函数的绝对地址** —— 先验不成立。代码段中间只要插进去一个函数，
  后面全部平移，位移量可以是几十 KB 甚至更多，不是"附近"，窗口扫救不回来。
  "骨骼与进度"那条链用到的几个 CPython 函数（`PyRun_StringFlags`/`PyGILState_Ensure`/
  `PyRun_SimpleString`/`PyErr_Print`）正因为如此，黑盒 `1.so` 一开始就是用**特征码扫描**
  而不是硬编码地址去定位的 —— 即便这样，热更后特征码本身也会失配而整条链哑火
  （见 `逆向存档\2026.0611.0155\offsets\known_offsets.md` 第五节）。
  这类东西只能靠签名/字符串锚点重找，跟对象偏移失效是两码事。

推论：**凡是要记的偏移，优先记成"相对某个结构体基址的字段偏移"，
少记"相对模块基址的绝对地址"** —— 前者扛热更，后者不扛。

## 修复原则：不要写死新数值，改成自愈

这次的两处修复都没有简单地把 `0x430` 改成 `0x440`，理由是那组指针会整体位移，
写死任何一个下次还会废。已经落在 `draw_Gui.cpp` 里的做法：

**矩阵根**（`draw_Gui.cpp` 约 620 行）：在 `+0x300~+0x500` 窗口里找"整条链都走得通"的槽位
（`p1` 在 `(0x5000000000, 0x8000000000)` 区间 **且** `p1+0xa58` 也在该区间），命中即用。

**相机坐标**（新增 `取相机偏移()`，Draw_Main 上方）：VP 矩阵能反解出相机世界坐标
（行向量约定 `clip = world * M`，相机 = `-t * A⁻¹`，A是左上3x3，t是第3行），
实测与真实字段差约 6 单位 / 0.5 游戏米——精度不够直接用，但**足够当校验器**：
在 `-0x400~-0x40` 窗口里扫，谁最接近反解值谁就是真的。找不到退回旧值，最多试 60 帧。

面板加了一行 `相机偏移` 显示命中结果。日志关键字：`[矩阵命中] ... 槽位=+0x440`、`[相机命中] ... 误差=`。
（**2026-09-24 相机偏移这套已作为死代码删除**，见「矩阵链」节；`[相机命中]` 日志不会再出现。）

版本管理：`IdentityV` 是 git 仓库，直接用 git，不要再建 `.bak_<日期>` 副本。

**排查完记得清理**：这轮教训 —— 为定位问题加的计时日志、面板计数器、临时重定向的日志路径，
用完必须全部删掉再交付。交付前跑一遍 `git diff` 自查，别把调查脚手架当成功能留在源码里，
尤其别留下**后来被数据推翻的注释**（当时写的"首趟遍历要 5~10 秒"就是反例）。

## 纠正：以前记错的东西

**旧版 skill 和 known_offsets.md 写着"第一步 `strings libclient.so | grep -i GameObject`
确认签名字符串还在不在"——这是错的，照做会把人带沟里。**

实测：`(PerObje` 这 8 个字节在 175MB 的 `libclient.so` 文件里**0 命中**
（单独的 `PerObject` 有 11 处，但都是 `PerObjectCBuffer` 这类 shader 常量缓冲区名，不带左括号）。
它是**运行时在可写段里构造出来的字符串**，不是静态 .rodata 串。

所以：**静态 strings 判断不了签名死没死，必须上机读 bss**。按旧指引走会误判成"引擎大改"。

**指针高位的 `0xB4` 不是 NeoX 自己的 GC/类型标签方案** —— 那是 **Android 的堆指针标记
（TBI，固定 tag 0xB4）**。所以它对**所有 malloc 出来的指针**都成立，不止引擎对象，
Python 对象也一样。掩码 `& 0x00FFFFFFFFFFFFFF` 照旧，但别再按"引擎特有"去理解它。

**内嵌的 CPython 是 3.11，不是 2.7。** 判据：dict 用 `PyDictUnicodeEntry{key,value}` 16 字节
（3.11 引入、不存 hash），`PyLong` 仍是 ob_size 语义（3.12 会是 lv_tag），
managed-dict 实例的 dict 指针在对象前 `0x18`。`known_offsets.md` 里关于注入子系统的分析
是按老版本 CPython 假设写的，要按 3.11 重新对。

**清后台不一定能缓解内存压力，反而可能更糟。** 2026-09-21 实测：清完后台系统层面松了
（MemAvailable 1.03→1.40 GB），但**游戏自己被一起切到后台**，`VmRSS` 869→596 MB、
`VmSwap` 1296→1386 MB。换出的页只有游戏**真的去访问**时才换回来，
所以正确做法是回到游戏里动一动（走动/转视角）再量，光停在那里不会恢复。
判断"数据能不能用"别只看 `VmSwap` 绝对值，看**类名读出率**（健康 65~72%，56% 勉强可用，14% 是病态）。

## 性能基线（2026-09-23 实测，做优化前先看这里）

**怎么测（不用改代码，随时可做）**：叠加层是多线程进程，读 `/proc/<pid>/task/*/stat` 的
第 14/15 字段（utime/stime，单位 10ms），间隔采样算差值，就能拿到**每个线程**的 CPU。
识别线程靠节奏：读线程 3 秒一个脉冲，`PySelf` 16ms 近似连续，`PyGenius` 500ms。
精度受 jiffy 限制（±10ms），一轮只有 7~8 个 tick 时误差约 ±12%，**分不出 10% 以内的差别**。

| | 实测 |
|---|---|
| 单次驱动读（一次 `ioctl`） | **约 3~4µs**（由读线程一轮 2100 次读 / 8.7ms 反推） |
| 读线程一轮（约 300 个对象） | 优化前 **12ms**，优化后 **9~10ms**，占 CPU 0.3~0.4% |
| **渲染线程** | **约 4.4%，优化前后没变化** |
| 三个 Py 线程 | 合计约 2.6%，最忙的(`PySelf` 16ms)约 1.0% |
| 全进程 | 约 8% |

### ★ 结论一：渲染线程是**固定成本**，跟场上实体多少无关

2026-09-23 同一版本、同一台机器，大厅和局内各测 24.5 秒：

| | 大厅 | 局内 |
|---|---|---|
| 渲染线程 | **4.41%** | 4.37 / 4.42% |
| 读线程 | 0.33% | 0.29~0.33% |
| 全进程 | 7.27% | 7.6~8.2% |

**两边一模一样。** 所以 4.4% 花在 ImGui 生成几何 + 每帧提交上，不随实体数变。
由此**否决两条优化提案**（别再提）：

- ~~绘制侧每帧的 `std::string` 拼接 / `ostringstream` / 反复 `strstr` 改 enum+switch~~ ——
  理论上限只有约 0.9%，而实测连这个量级的差异都没显现。
- ~~`PySelf` 的本体集合从 16ms 降到 100~200ms~~ —— 最多省 0.5~0.8%，
  代价是切形态后 100~200ms 内集合是旧的（红蝶/无常会短暂错画），不值。

（一个限制：大厅里场景数组同样约 300 个对象，所以"大厅=没实体"不严格成立。
要完全干净得把绘制开关全关掉再测一次。但既然理论上限本就不到 1%，没有继续投入的必要。）

### ★ 结论二：渲染线程的开销**不是**驱动读，别再往那个方向优化

删掉每实体每帧 4 次读取（`+0x70`/`+0xaa` 两次死读 + 三个坐标合并成一次）之后，
渲染线程从 4.5% 变成 4.4%，**在噪声里**。所以它的大头是 ImGui 绘制和每帧图形提交。
我曾用"每实体每帧约 8 次读 × 30 实体 × 60fps ≈ 4.3%"反推说明它全是读取，
**那个吻合是巧合**，实测推翻了。以后再有"砍每帧读取次数来提性能"的提案，先引用这一条。

读线程那边的优化**是有效的**（类名缓存），而且它才是"扫描间隔能不能从 3 秒缩短"的关键：
按一轮 9ms 算，改成 1 秒是 0.9% CPU、撕裂窗口 0.9%。

### ★ 叠加层内存：216MB → 110MB（2026-09-24，产物 `fltupird.sh`，上机通过）

面板原来的「内存占用」读 `statm` 的 RSS（约 22MB），**漏了 90%**。实际大头是图形：

| | 优化前 | 优化后 | 读法（进程内可读，面板现在就这么算）|
|---|---|---|---|
| 画面缓冲（交换链 dmabuf）| **157MB**（4 张 3200×3200）| **70.7MB**（4 张 3200×1440）| `/sys/class/kgsl/kgsl/proc/<pid>/imported_mem`（字节）|
| GPU 私有显存 | 19.8MB（字体纹理 2048² RGBA 占 16MB）| 19.8MB | 同目录 `kernel` |
| 进程 PSS | 5.9MB | 7.4MB | `/proc/self/smaps_rollup` `Pss` |
| 已换出 | 33MB（字体图集 CPU 副本 20MB 在里面）| 12.2MB | 同上 `SwapPss` |

非高通没有 kgsl 目录，面板退回 `/proc/self/fdinfo` 累加 dmabuf `size:`，显存标"未计"。
`dumpsys meminfo <pid>` 的 `EGL mtrack` 就是画面缓冲，**Vulkan 私有显存它看不到**，别拿它当总数。

三处改动：
1. **`main.cpp` 表面改横屏**（`native_window_screen_y` 取短边）。原来长×长正方形是为了竖屏也铺满。
   代价：竖屏时只显示上面 1440 行（游戏只有横屏，无所谓）。录屏穿透重建路径用同一组变量，自动一致。
2. **`imgui_impl_vulkan.cpp` 交换链尺寸用传入值、不用 `currentExtent`**（第三方库本地修改，带注释）。
   我原以为 Android 在旋转 90° 时会把 `currentExtent` 宽高对调，所以加了这个保护。**实测这台机器没对调**：
   日志 `[交换链] 请求=3200x1440 currentExtent=3200x1440 currentTransform=0x2(ROTATE_90)`。
   所以这里不是必需的，但无害，换设备时能防一手。那行日志每次建交换链都会打。
3. **`main.cpp` 每帧 `EndFrame()` 之后，若 `TexID` 非 0 且 CPU 像素还在就 `ClearTexData()`**。
   必须在 EndFrame 之后（NewFrame~EndFrame 图集加锁；release 构建断言被关掉，写错位置也不报错）。
   按状态判断而不是只做一次，是为了覆盖 ImGui 上下文重建。

顺带查清：**录屏穿透(`permeate_record_ini`)是死代码** —— 原版那个「过录制」复选框在 `IdentityV` 里已删，
没有任何地方置 true，`drawBegin()` 里那段重建永远不执行，`permeate_record` 恒 false。

还能省但没做：交换链 4 张（`m_MinImageCount=2`，驱动 `cap.minImageCount` 抬上去的，不一定改得动）；
字体按 `ChineseFull` 范围建了 6998 个字形的 2048² 图集，换成只含实际用到的字能把 16MB 显存压到几 MB。
⚠ 裁字符集要先确认没有显示任意文本的地方（比如以后要显示玩家昵称），否则生僻字会变成方块。

### 运行日志：PC 侧可以直接读，别让用户复制粘贴

文件是 root 建的 0644，**shell 用户有读权限，adb 可以直接 pull，不用 su**
（走 `su -c cp` 反而容易静默失败，表现是 pull 到的还是上一次的旧文件）：

```powershell
$adb = "C:\Users\31297\AppData\Local\Android\Sdk\platform-tools\adb.exe"
& $adb pull /data/local/tmp/hack_stdout.log "$env:TEMP\procmem_tmp\overlay.log"

两个必须知道的性质（都是原版设计，不要想当然）：
- **`O_APPEND` 追加，永不截断**。实测已攒到 260 KB / 59 次运行混在一起。
  **本次运行从最后一个 `[基址]` 开始**，别直接 `tail` 就下结论：
  ```powershell
  $lines = Get-Content $f -Encoding UTF8
  $idx = @(0..($lines.Count-1) | Where-Object { $lines[$_] -match '\[基址\]' })
  $lines[$idx[-1]..($lines.Count-1)]      # 最后一次运行
  ```
- **stdio 重定向到文件后是全缓冲**，printf 要攒满 4KB 才落盘。日志尾部可能缺最后几行，
  而那恰好是出问题时最想看的。要精确计时/抓崩溃前最后几行，得临时加
  `setvbuf(stdout, NULL, _IONBF, 0)`，**用完记得删**。

### ！！推送产物：放 `/data/` 根目录，不要放 `/data/local/tmp/` ！！

**用户明确要求（2026-09-21）。** 以后推叠加层产物一律落到 `/data/<名字>.sh`。

`/data` 是 `drwxrwx--x root:system`，**adb shell(shell 用户) 写不进去**，所以不能直接
`adb push /data/xxx.sh`。要经 sdcard 中转（**不要**拿 `/data/local/tmp` 当中转站）：

```powershell

& $adb shell "su -c 'cp /sdcard/$mod.sh /data/$mod.sh && chmod 755 /data/$mod.sh && md5sum /data/$mod.sh'"
& $adb shell "rm -f /sdcard/$mod.sh"
```

推完对一下 md5 再让用户跑。运行：`su -c /data/$mod.sh`。

**坑**：在 Bash 工具里跑 adb，`/data/local/tmp/x` 这类参数会被 Git Bash 改写成

**adb 命令一律用 PowerShell 工具跑**，别用 Bash。

**坑**：`Push-Location` 不会改变 .NET 的当前目录，所以 `[IO.File]::ReadAllBytes(".\x.sh")`
这类调用必须传绝对路径，否则会去工作目录找而报"文件不存在"。

## 关键背景知识（避免重复踩坑）

- 设备 root 可用（Magisk，`su -c` 有效），**所以 PC 侧能直接读游戏内存做验证，不用每次改代码重编译**。
  这是这轮效率提升最大的一点。但要遵守安全读取规则，见 `android-re-toolkit`。
- 目标进程 stdio 默认全缓冲，注入代码里的 `printf` 不会立刻落盘，需要远程 `fflush(NULL)`。
- `/data/local/tmp/` 不是世界可写（`drwxrwx--x`）：**adb shell(shell用户) 能写**，
  但**游戏 app 进程写不进去**会 `EACCES`。要让游戏自己写文件，用
  `/sdcard/Android/data/com.netease.dwrg/files/`。
- 同一个游戏进程只要没重启，`.so` 一旦 `dlopen` 过就判定"已加载"，改完注入代码必须
  **彻底重启游戏进程**（不是切后台）才能验证。这条最容易被忽略，要反复提醒用户。
- 引擎是网易自研 NeoX，不是 Unity/IL2CPP，`libclient.so` 里没有 `il2cpp`/`GameAssembly`，
  Il2CppDumper 完全用不上。
- 游戏内嵌 CPython 静态编译进 `libclient.so`，核心 API（`PyGILState_Ensure` 等）没导出到
  动态符号表，`dlsym` 走不通，只能特征码扫描——这是"骨骼与进度"子系统的根本难点，
  跟对象偏移失效是**两个完全不同性质的问题，不要混为一谈**。
- 约瑟夫的相机 `chr\boss\joseph\h55_joseph_camera.gim` **每局都会默认加载十几个**，
  跟这局有没有约瑟夫无关，是场景资源，代码里本来就有排除项。别当成误判去查。
- 红蝶/红夫人会切换形态（`h55_banshee.gim` ⇄ `h55_banshee_opposite_hx.gim` 是同一个人），
  做"自身锁定"优化时要按翻译后的名字续锁，不能按原始地址。
- **启动链路已实测，别再怀疑它慢**：从 `read_thread` 进入到首个实体发布，六次运行
  全在 **26~43 毫秒**（签名扫描 5ms、首趟遍历 1ms）。用户报"开着面板等了几秒才出图"时，
  **原因一定在游戏侧或内存侧，不在叠加层启动链**。曾经推断过"首趟遍历耗时 5~10 秒"，
  被计时日志直接推翻 —— 对局中 `Count` 只有 274~307，跑完不到半秒。
- 面板上的 `数据获取状态` 是死变量（`数据获取状态` 从未被赋值，恒为 0），别拿它判断任何事；
  真正的状态是 `状态`：0=还在读 bss 找签名（此时 `Draw_Main` 整个早退，什么都不画）、
  1=数组失效重试中、2=正常。
- `监管者预知` 是扫到一半就写的，`数量` 是整趟扫完才发布的（`数量 = 指针数量` 在循环外）。
  理论上首趟扫描期间会出现**面板样样正常（状态=2、矩阵/数组地址都有、监管者已识别）、
  屏幕却是空的**。但实测这个窗口只有约 1 毫秒，**不足以解释任何肉眼可见的空窗**。
  曾经为它加过"边扫边发布"补偿（`if (数量 == 0) 数量 = 指针数量;`），计时数据出来后
  确认无实际收益**已移除**，别再加回去 —— 真因见上面的内存压力那节。

### 形态切换（红蝶）与"废弃模型" —— 2026-09-22 实测，有精确判据了

红蝶换形态**不是换操控对象**（`cam.unit` 不变），是同一个 unit 换模型。
旧形态的场景对象**留在数组里、仍被绘制循环捕获**，这就是"废弃模型"。

单位上是一对模型对象：

```
unit.model          当前形态   .visible == True
unit.another_model  废弃形态   .visible == False
unit.model_path     当前形态的 .gim 路径, 如 'chr/boss/banshee/h55_banshee.gim'
```

**★ 判据：`another_model + 0x20` 就是废弃模型的场景对象指针。**
实测红蝶一局：`model+0x20 = 0x7ACBDFFF80`（在画的那个）、
`another_model+0x20 = 0x7ACDDD0600`，后者与用户独立抓到的废弃对象地址**逐位相同**。

每帧对每个玩家单位读一次 `another_model+0x20`，拉黑那个地址即可。
**这可以替掉下面那份红蝶/木偶师类名黑名单**，精确、跟视角无关、不用维护名单。

### ★ `model.visible` 就是 `+0x73`

同一角色一真一假两个场景对象做 768 字节逐字节 diff，已知语义字段里**只有 `+0x70` 干净分开**：

| 字段 | visible=True | visible=False |
|---|---|---|
| **`+0x70`** | `00 00 00 01` | `00 00 00 00` |
| `+0x240` | **2** | **2** ← 两个都是 2，**挡不住废弃模型** |
| `+0x1a0` | 450.0 | 450.0 ← 相同 |
| `+0x6D` | 0x50 | 0x50 ← 相同 |

所以本文件里"`+0x73 == 1` ⇔ 当前对本机客户端可见"这条**完全正确**，现在有了引擎侧的名字
（NeoX 模型对象的 `visible` 属性）。

⚠️ **但仍然不要拿 `+0x73` 当过滤器。** 它是渲染剔除的结果，
**远处的真实对象同样 `visible=False`**。废弃模型恒不可见，但不可见的不一定是废弃模型 ——
用它过滤会重演"求生者只看得到身边的密码机"。**要用 `another_model+0x20`，不是 `+0x73`。**

~~⚠️ 道具的废弃模型还没验。~~ —— **2026-09-22 验了一半：宿主判据成立。**

一局里 `chr\prop\h55_pendant_dart\h55_pendant_dart.gim` 有 3 个对象，
从 Python 侧反查宿主：**只有 1 个出现在 `unit.item_lst[0].model` 上**，
另外 2 个无宿主。三者的 `+0x6D` 分别是 `0x50` / `0x10` / `0x10` —— 真的那个带 `0x40`。

```
★ 道具真假 = 是不是某个 unit 的 item_lst[i].model（指针身份）
  场景侧近似判据 +0x6D & 0x40 在挂件族上与它一致
```

⚠️ **`& 0x40` 不能推广到角色的备用形态**：`h55_survivor_m_muou_puppot.gim`
是废弃形态（`+0x70 = 0`）却是 `0x50`、**照样带 `0x40`**。
`0x40` 的语义是"是不是角色/生物实体"，不是"活跃/废弃"。

还缺的对照：**掉在地上的真道具有没有宿主**（那局 5 个道具全在手上，没得测）。

> 顺带修正 `idv-replay-genius` 里记的人偶 `+0x6D = 0x90`：**实测是 `0x10`**。
> 而且同一个对象的 `+0x6D` 会跳变（木偶师本体两次采样 `0x50 → 0xD0`），
> 但 **`0x40` 位在两次采样里都稳定** —— 拿 `& 0x40` 做判据不受影响，
> 拿整字节比对则会翻车。这也再次印证 `+0x6D == 0xD0` 跟"自身"无关（早已证伪）。

历史记录（保留以免重复走弯路）：已排除的候选有 `+0xaa` 完整字节（是通用状态位）、
全模块内存反查自身地址（6局全 0 命中）、`+0x6D == 0xD0`（瞬时值，已证伪）。

## 绘制循环里已有的过滤（别重复造轮子）

`draw_Gui.cpp` 实体绘制循环开头已经有这些，加新过滤前先看一眼免得重复：

```cpp
D.X = +0xa0   D.Z = +0xa4(高度!)   D.Y = +0xa8      // 注意代码里 Z 才是高度
if (类名含 "buzz") continue;                        // 跳过特效
if (类名含 "nvyao.gim") continue;                   // 跳过女妖蜡烛
if (D.X==0 || D.Y==0) continue;                     // 跳过原点
if (D.Z <= -300) continue;                          // 跳过地下
if (距离 >= 300) continue;
if (W > 0) { ...绘制... }                            // W<0 自然剔除了相机背面的对象
```

**关于"原点"**：实测近原点的 18 个对象坐标全是**精确 `0.0`**（原始位 `00000000`），
不是 `1e-8` 这种极小值，所以 `D.X==0` 这个精确比较是挡得住的，不需要加 `fabs()<1e-5` 容差。
（用户曾怀疑需要容差，实测否定。如果再遇到"物体一直画在原点"，原因在别处，
别再往这个方向查——多半是屏幕坐标问题而不是世界坐标。）
